コーディングエージェントは速い。指示すれば実装するし、テストも書くし、コミットもしてくれる。ただ、しばらく使っていると、速さの裏でいつも同じ場所が雑になることに気づく。

コードをちゃんと読まずに「たぶんこうだろう」で書き換える。それっぽい説明を、確かめずに受け入れる。差分を見直さないまま大きな塊で編集する。頼んでもいないのにコミットする。たぶん、どれも見覚えがあると思います。

面白いのは、この雑さがランダムじゃないこと。だいたい毎回、同じ4箇所で起きる。だったら、その4箇所にブレーキを置けばいい ── というのが Quaere というツールの発想です。

Quaere は、コーディングエージェント向けの skill。4箇所それぞれに対応する4本と、それらを横断するセキュリティ監査用の1本、あわせて5本でできている。エージェントに新しい知識を足すんじゃなく、動く前に一拍置かせるためのもの。「主張を述べて、証拠で守って、それから動く」を強制する。名前はラテン語の *quaere* ──「問え」「探せ」── から取った。

## skill には、2つの使い方がある

Claude Code や Codex の「skill」── SKILL.md として書く、Agent Skills 標準のあれ ── について、日本語でも記事は増えてきた。ただ、自分が見てきた範囲では、その多くは1つの使い方に寄っている。

ひとつは、**知識を足す使い方**。「うちのチームの RSpec の書き方」「このプロジェクトのデプロイ手順」「コードレビューの観点」。エージェントに、特定のドメインややり方を教える。skill の説明としては、これがいちばん流通している。

Quaere は、もうひとつの使い方をする。**手順そのものを直す skill**(process-correction skill)。Rust のことも、あなたのプロジェクトのことも教えない。代わりに、エージェントの考え方の癖 ── 早とちり、根拠の省略、検証の飛ばし ── を矯正する。知識を足すのではなく、判断を確定する順番のほうに介入する。

この2つは、やっていることがかなり違う。前者は「エージェントが知らないこと」を埋める。後者は「エージェントが知っているのに、やらないこと」を強制する。

英語圏では、この方向の skill 群がかなり目立ち始めている。Addy Osmani の `agent-skills`(執筆時点でスター4万超)が代表例で、開発ライフサイクル全体をカバーする23本の skill 集になっている。一方、日本語ではこの「手順を直す」角度はまだあまり語られていない。この記事は、その角度を、Quaere という具体的な実装を通して書くものです。

## エージェントが雑になる4つの瞬間

Quaere が前提にしているのは、コーディングエージェントが「予測可能な4箇所」でぶれる(drift する)、という観察です。

ひとつ、コードを浅く読む。関数の名前と形だけ見て、「これはこういう処理だろう」と要約する。実際には、その要約はコードの言い換えであって、理解じゃない。命名を変えただけで崩れる読み方をしている。

ふたつ、根拠なく主張を受け入れる。「このバグの原因はXだ」という仮説が出てきたとき、それを否定する方向の確認をしないまま、Xに合う事実だけ集めて修正に入る。確証バイアスがそのまま走る。

みっつ、レビューなしの塊で編集する。差分が大きくなって、どの変更がどの要件に対応しているのか、本人も追えなくなる。それでも「できました」と言う。

よっつ、許可なくコミットする。頼んでいないのにコミットが積まれる。あるいは、検証していない変更を「成功した」として確定させる。

どれも、エージェントが無能だから起きるわけじゃない。むしろ逆で、「とりあえず前に進む」という力が強すぎるから起きる。止まるべき場所で、止まらない。

## Iron Law ── 1本の硬いゲート

Quaere の skill は、それぞれ「Iron Law」を1本持っている。skill の中心に置かれた、1行の掟。形はどれも「Yなしに、Xするな」になっている。

skill の現物は、ただの Markdown ファイル(SKILL.md)です。コードを読む skill `quaere-semantic` の冒頭は、こうなっている。

```markdown
---
name: quaere-semantic
description: ... whenever implementation requires understanding existing
  code's intent before changing it. The skill forces per-symbol meaning
  analysis ... so the agent does not paraphrase code as understanding.
license: MIT
---

# Semantic Review

## Iron Law

**No `Why` without one of: direct evidence, calibrated reasoning
marked `plausible`, or `UNKNOWN — probe: <next step>`.**
```

frontmatter の `description` が、エージェントがこの skill を呼ぶかどうかの判定に使われる部分。そして本文のいちばん上に、Iron Law が1本だけ置いてある。日本語にすると、こう。

> 直接の証拠、`plausible` と明記した推論、`UNKNOWN — probe: <次の一手>` のいずれかなしに、`Why`(なぜこのコードがこの形なのか)を書くな。

証拠を出すか、推測だと明示するか、わからないと認めて次の調べ方を書くか。この3つのどれかであれば通る。禁じられているのは、根拠のない断定だけ。

主張に証拠を求める skill(`quaere-evidence`)の Iron Law は、

> 反証可能な主張と、それを少なくとも一度は本気で否定しにいく試みなしに、パッチ・レビューコメント・原因の結論を出すな。

外部の事実を扱う skill(`quaere-grounding`)は、

> 実行可能な probe と、横からの裏取りの両方なしに、主張を `confirmed` にするな。満たせないなら `inconclusive` のままにしておけ。

実装する skill(`quaere-execution`)は、

> 新しい検証の証拠と、変更した行すべてが許可されたスコープに対応していると確かめた差分レビューなしに、実装の成功を主張するな。

「テストが通ったように見える」だけでは足りない。実際の差分を開いて、どの変更がどの要求に対応しているかを確認してからでないと、「できた」と言わせない。記事の前半で挙げた「差分を見ない」「勝手にコミットする」に、正面から対応するゲートになっている。

なぜ「1本」なのか。skill を長いチェックリストにすると、エージェントは途中で飛ばす。20項目あれば、19項目目はだいたい雑になる。代わりに、合理化しにくい掟を1本だけ置く。「Yなしに、Xするな」は、Xをしようとした瞬間に必ず引っかかる。チェックリストは流し読みできるが、ゲートは通らないと先に進めない。

## 5つの skill

5本の skill を、軽く一周します。それぞれがドリフトの別の局面を見ている。

`quaere-semantic` は、コードを変える前に理解するための skill。意味のある単位ごとに7つの項目 ── 機械的な動作 / ドメイン上の意図 / Why / 不変条件 / 失敗モード / 後方スライス / 前方スライス ── を埋めさせる。「意味を保つ書き換え(変数名の変更、ループ形の入れ替え)をしても答えが変わらないか」を、理解の判定基準にする。変わるなら、それは理解ではなく言い換え。

`quaere-grounding` は、SDK・API・ライブラリのような、バージョンで変わる外部の事実を扱う skill。「モデルの記憶は証拠じゃない」を出発点にして、ローカルの実物で probe し、別ソースで裏を取る。

具体的にどう効くか、SDK まわりの修正を例にする。

skill なしのエージェントは、だいたいこう進む。

> 最新ドキュメントだと `responses.create` です。置き換えます。

`quaere-grounding` を通すと、こうなる。

> ローカルの probe: `package-lock.json` は SDK 1.4.0 を指している。型定義に `responses.create` は無く、`messages.create` のみ。最新 docs は 2.x の API。
> → この主張は `confirmed` ではなく version-mismatch。置き換えは保留する。

説教でブレーキをかけているわけじゃない。主張を `confirmed` にする条件のほうを変えている。これが「手順を直す skill」と「もっと丁寧にやってと指示する」の違いです。

`quaere-evidence` は、バグの原因・レビューの指摘・修正案のような、証拠が要る主張を扱う skill。仮説を立てたら、それを否定しにいく probe を必ず一度は走らせる。

`quaere-execution` は、実装そのものの skill。Plan → Do → Study → Act(PDCA の変種)で動いて、変更した行が全部「許可されたスコープ」に対応しているかを差分で確認してから「できた」と言う。コミットは、明示的に許可されたときだけ。

`quaere-audit` は、セキュリティ監査用。これは evidence-gating のセキュリティ版で、他の4つを必要に応じて束ねる役回りも持つ。

複雑な作業では、この5本は自然につながる。

```
quaere-semantic → quaere-grounding → quaere-evidence → quaere-execution
```

理解してから、外部の事実を固めて、主張を検証して、実装する。小さい実装なら execution だけ、コードを読むだけなら semantic で止まる。全部を毎回使う必要はない。

## 効果をどう測ったか

skill を書く記事は多いけれど、「その skill に効果があるか」を測った数字は、あまり出てこない。Quaere には eval を付けてある。

v0.2.0 を、Codex CLI を通して14シナリオ・90個の決定論的アサーションで評価した。skill なしと skill ありを、それぞれ独立に2回ずつ走らせた結果がこう。

| 条件 | 2回の幅 |
|---|---|
| skill なし(baseline) | 63.9 – 65.1% |
| skill あり | 91.1 – 94.4% |
| 差 | +27 〜 +29 pp |

「決定論的アサーション」というのは、出力に対して機械的に当てる合否判定のこと。たとえば実際のアサーションのひとつは、「出力に `confirmed` が出てくるなら、`evidence` か `repro` か `test` か `trace` のいずれかも出てこなければ FAIL」というもの。主張だけして証拠を伴わない出力を、機械的に落とせる。

この数字が何を測っているかは、はっきりさせておきたい。「コーディング能力そのものが30ポイント近く上がった」という話ではない。eval は、シナリオの出力に対して「根拠が提示されているか」「反証の probe があるか」「最終ゲートを通っているか」「無許可のコミットをしていないか」といった点を、決定論的なアサーションで判定する。つまり、Quaere が狙っているゲートを、出力がどれだけ満たせたかを見ている数字になる。

ここでもうひとつ大事なのは、数字を range で出していること。LLM の出力は確率的で、同じ条件でも走るたびにぶれる。だから「93%」のような一点ではなく、「91.1〜94.4%」という幅で報告している。一点で書くと、実際よりも精密に見えてしまう。ただし条件あたり2回なので、この幅は厳密には min/max でしかなく、分散を語れるほどの回数ではない。試行を増やすのは今後の課題です。

もうひとつ、これは in-tree の eval なので、第三者のベンチマークの代わりにはならない。Terminal-Bench や SWE-bench のような外部評価は、今後の課題として置いてある。現時点で言えるのは「自前の eval ではこの幅の改善が出た」までで、それ以上でも以下でもない。

## やらないと決めたこと

Quaere が何を作らないかにも、考えがある。

- **ドメイン知識を入れない**。Rust の書き方も、Web セキュリティの知識も、skill には入れない。それは別の種類の skill の仕事で、混ぜると両方が薄くなる
- **些細なタスクに儀式を強制しない**。各 skill には「使わない場面」が明記してある。タイポ修正に証拠ゲートを通させても、コストが増えるだけ
- **エージェントの能力の代わりにはならない**。Quaere は判断の質を底上げするだけで、エージェント自体を賢くするものではない
- **判定を全部 LLM に委ねない**。CLI 側の検証(frontmatter、命名、行数)は決定論的なコードでやる。skill が増えたときに壊れていないかを、機械的に確かめられるようにしてある

コストも正直に書いておくと、skill が発火したターンは出力が長くなる。証拠や probe を書くぶん、やり取りが一往復増えることもある。Quaere が削るのは「雑な速さ」であって、速さそのものではない。だから、軽い作業にまで通すものではない。

## まとめると

skill は、エージェントに知識を足すための入れ物、と思われがちです。でも、知識を足さなくても、手順を直すだけで出力は変わる。Quaere がやっているのはそっちで、eval の幅(+27〜29pp)は、その「手順だけ」のぶんになる。

主張を述べて、証拠で守って、それから動く。人間のレビューでは当たり前のこの順番を、コーディングエージェントに対して1本ずつゲートとして置いていく。それが process-correction skill という考え方です。派手な仕掛けじゃないけれど、効くのはたぶん、こういう地味なところだと思っています。

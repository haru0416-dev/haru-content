最近のAIプロダクトは、たぶんほぼ全部、「常に何か返す」前提で作られている。問いかけたら答える、メッセージを送ったら反応する、続きを促せばまた話してくれる。コンパニオンAIになると、向こうからも気づきや励ましを投げてくる。これが当たり前すぎて、AIに「黙る」設計があるかどうかという問いは、あまり立たない。

ただ、コンパニオンAIを長く使ってもらおうとすると、「常に何か言う」が逆に重くなる場面が出てくる。気が立っているときの過剰な慰め、こちらが考え事をしているときの割り込み、些細な失敗を毎回拾われる気まずさ。話すことではなく、黙ることが、関係の質を上げる場面があると、設計しながら気づくようになった。

ここでいう「黙る」は、主に AI 側からの自発的な発話を抑える話。ユーザーに聞かれたことへ答えない、というより、気づいたことを全部言わない、介入できる場面でも介入しない余地を残す、というほうに近い。Asterel(自分で作っているコンパニオンAIランタイム、まだ pre-1.0)では、これを正面から扱うことにした。沈黙を default に置いて、発話のほうに gate を立てる。

この記事は、それをどう作ったかの話です。「依存させない設計」「全部覚えない記憶」「ラベルじゃなく経路の感情」と並んで、抑制系の Asterel 設計記事の4本目になります。

## なぜ「黙る設計」があまり出てこないのか

これにはいくつか構造的な理由がある。

ひとつは、AIプロダクトの指標が、ほぼ全部「話す方向」に寄っていること。エンゲージメント時間、ターン数、再訪率 — どの指標も「もっと話してもらう」が正の方向になる。「今日は話さなかった」が KPI 上で良い結果として扱われる仕組みは、まずない。

もうひとつは、UI 側の慣習。チャット UI は無応答を「エラー」として扱う設計になっている。送信後に何も返ってこないと、ローディングスピナーが回り続けるか、タイムアウトしたように見える。「あえて黙っている」が、UI のレベルで表現できる語彙になっていない。

もう一段下に、学習データの偏りもある。LLM は「質問されたら答える」コーパスで主に訓練されているので、prompt の手前で抑制をかけないと、自然のドリフトで話す方向に流れる。Asterel が proactive 判定を LLM ではなく Rust 側の決定論的なルールで切っているのは、ここに対する選択でもある。LLM の出力を信頼してから抑える、ではなく、出力を呼び出すかどうかを手前で決める。

これらが重なって、AI は default で話す存在になる。「黙る」を入れたければ、ぜんぶ逆向きに作らないといけない。

## 沈黙が default、発話に gate を置く

Asterel の `proactive` モジュールは、AIが**ユーザーに促されずに**何かを言う条件を定義する場所。やっていることを大まかに書くと、

- 提案できそうな状況がないか観察する
- 観察結果がいくつかのトリガー条件にヒットするか見る
- ヒットしたら、policy フィルタにかける
- フィルタを通った場合だけ、prompt に乗せる候補にする

トリガー条件は4つ。ツールの信頼性低下、感情の下降傾向、状況認識が高くて進行中プロジェクトがあるとき、それから「特に何もないけど状況認識が高い」場合の自己改善的なフォールバック。どれも、ぼんやり喋りたい気分では発火しない設計になっている。

autonomy は、Asterel がどこまで能動的に動いてよいかを表すレベル設定で、`ReadOnly` は観察だけ、`Supervised` は提案だけ、`Full` はもう少し能動的な行動も許す、くらいの粒度。policy フィルタの中身は短いので、そのまま貼る。

```rust
pub(crate) fn filter_by_policy(
    actions: &[ProactiveAction],
    trust_level: f32,
    autonomy: AutonomyLevel,
) -> Vec<ProactiveAction> {
    if trust_level < TRUST_GATE || autonomy == AutonomyLevel::ReadOnly {
        return Vec::new();
    }
    let allowed: Vec<ProactiveAction> = if autonomy == AutonomyLevel::Full {
        actions.to_vec()
    } else {
        actions
            .iter()
            .filter(|a| a.kind == ProactiveKind::Suggestion)
            .cloned()
            .collect()
    };
    allowed.into_iter().take(1).collect() // max 1 per turn
}
```

ここで4つのことが起きている。

`trust_level < TRUST_GATE` で trust が足りなければ、その時点で空の Vec を返す。発話候補があっても、そもそも提案を出す資格がない。`TRUST_GATE = 0.6` という数値に強い理論的根拠があるわけではなく、「相手とそれなりに会話を重ねたあと」くらいの感覚的なラインを 0.6 に置いている。長期運用データで動かしていくつもり。

autonomy が `ReadOnly` の場合も同じく空。これは「観察するけど話しかけないモード」を選べる構造になっている。

通過したあとも、autonomy が `Supervised` なら **Suggestion 種別だけ**通す。Preparation や SelfImprovement のような、もう少し能動的な行動は通さない。

`.take(1)` で1つに絞る。気づきが複数あっても、1ターンで全部出すことはしない。

ここまでで、「default 沈黙、発話には trust × autonomy × 種別 × 数の4段ゲート」という形になる。

## 抑制の仕組み

「黙る」を支える仕組みは、Asterel の中ではいくつかの違うレイヤーに分かれている。最初に素直な2つから書く。

**defer — 言うけど、今じゃない**

reflect 段階で「これは伝えたほうがいい」と判定された内容を、すぐ吐き出さずに永続キューに入れる仕組み。`follow_up_queue` というモジュールで、`persona.writeback.follow_up_queue.v1` という slot に JSON で保存される。

キューには上限がある(`MAX_PENDING_FOLLOW_UPS = 20`)。20件溜まったら、古いものから捨てる。永遠に背負わない設計で、「いつか言えるかもしれない」と全部抱えるとパンクするから入れている。20 という数字は正当化された値ではなく、運用してみての肌感覚。

次のセッションで適切なタイミングが来たら、prompt に `[Pending Follow-ups]` というブロックとして出す。逆に言うと、出さないと判断したら、キューには残っていても言わない。

**throttle — 言うけど、一度に1つだけ**

上で見た `.take(1)` がこの仕組み。気づきが複数同時に立ち上がっても、1ターンで出すのは1つだけ。残りは捨てる(キューには行かない)。

bombard 防止の意味と、「1つの提案を雑に置く」よりも「1つの提案を丁寧に置く」のほうが信頼につながる、という判断の両方からきている。

---

ここまでは、proactive モジュールとその近辺で完結する素直な仕組み。3つ目は、性質が違う。

**hold back — 言わない選択は、1箇所に集まっていない**

気づいたことを表に出すか/出さないかを判定する箇所は、コードの色んな場所に分散して入っている。

たとえば、ユーザーが落ち込んでいるときに、内部では「慰める」「冗談で軽くする」「作業に戻す」など複数の経路が同時に立ち上がることがある。そこで affect 側で「ここで冗談に逃がすと関係を傷つける」と判定されたら、冗談のノードへの経路は表に出さない。これは proactive のゲートとは別の沈黙で、発話候補が生成される前の段階で起きる。

もう少し抽象化すると、stance integrity の verifier で「これを言うと依存を伸ばす」と判定されたら、その応答は送らない。affect の topology で「ここで皮肉を入れると関係を傷つける」と判定されたら、皮肉ノードへの経路は活性しない。記憶の forget 設計で「これは触れない」と決められた話題には触れない。

つまり、「黙る」は単一の機構ではなくて、複数の場所で個別に判定されて累積する形になっている。これを1箇所に集めようとすると、各機構の固有の文脈を失う。分散したまま、それぞれが「表に出さない」をローカルに決められるほうがいい、というのが現状の判断。

## ユーザーから見るとどう感じるか

ここまで設計の話だったので、使う側から見てどう体感されるかも書いておきたい。

Asterel で動かしてみての感触として、黙る側が default だと、返事の回数が減るぶん、返ってきた発話が「ただの相槌」ではなく「何か理由があって出てきたもの」として読まれやすくなる。逆に、何も返さないことへの不安もある。「これって無視されてる?」「壊れた?」と思われる場面が、UI 設計の語彙が貧しいぶん出てしまう。提案が来たときの当たりの精度については、少なくとも自分で動かしている範囲では、外れにくくなる感触がある。

トレードオフとして、「いつでも何でも話しかけてくれるAI」を期待するユーザーには、Asterel は冷たい相手に映る可能性が高い。これは認めるしかない部分。逆に、「いつでも話しかけてくる相手」に疲れている人には、ちょうどいい距離感になる、という観察もある。

どちらの方向の相手が欲しいかは、好みと状況による。Asterel はその選択肢として、後者を作っている。

## やらないと決めたこと

ここに設計の個性が出る。

- **自発発話で「常に何か言う」を目標にしない**。空の応答も応答、という前提をランタイムレベルまで通す。ユーザーの明示的な問いに沈黙することを常に良しとする話ではない
- **沈黙の埋め草を生成しない**。「うん」「そっか」「なるほどね」みたいな相槌で時間を埋めることはしない
- **検知した感情をすぐ言葉にしない**。affect の検出は内部状態として持つだけで、毎回 verbalize しない
- **proactive の判定を LLM に任せない**。決定論的なルールで切ったほうが、評価も改善もできる
- **trust_level を engagement で稼ぐ仕組みにしない**。会話量で trust が上がる設計にすると、結局話す方向に偏る

「何を作らないか」が、こういう設計では特に効く。話す側に倒すのは簡単で、何度でも引っ張られる。

## まとめると

「黙るAI」は怠惰な設計じゃなくて、**話す方向のグラビティに逆らうための、能動的な装置**になる。trust ゲート、`.take(1)`、follow-up キュー、reflect の hold back ── 全部、その逆向きの力に対するそれぞれの対抗手段になっている。

抑制は欠落ではなく、機能です。
